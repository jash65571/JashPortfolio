01 / CONTEXT

A job-search page is only useful if the data behind it is current, distinct, and searchable. The interface is the last step in a much larger system.

Job records arrive from different sources, with different titles, locations, formats, and update patterns. Search needs to make that information useful without turning every query into a scan of the whole dataset.

02 / ENGINEERING DECISIONS
01

Build the pipeline behind the listings.

The ingestion system brings together employer ATS adapters, feeder APIs, and direct job-search API results. Most sources land in a raw-job table first. A normalization process handles fingerprints and duplicates before promoting records into the main job table. Queued enrichment adds work model, seniority, and sector data.

02

Connect different hiring systems.

The codebase includes adapters for systems such as Greenhouse, Lever, Ashby, SmartRecruiters, and Workday. Source records hold adapter keys, board configuration, and polling settings. Scheduled jobs, retries, rate limits, and budget guards make collection an operating concern as well as an integration task.

03

Put search close to the data.

The documented search system uses weighted PostgreSQL full-text vectors for title, company, and description. A GIN index supports retrieval, and database functions return ranked IDs for the public search flow.

04

Treat public search as a real product.

The public job search uses URL-based queries and server rendering. Filter flows cover location, work model, job type, freshness, and salary data, while detail pages connect users to employer application pages.

05

Carry the workflow through to the resume.

The resume system covers PDF and DOCX uploads, per-user file storage, structured resume data, inline edits, job-specific tailoring, and document export. Separate API routes and UI steps connect upload, parsing, review, and download. Account and extension features make this a complete product beyond the public search page.

06

Learn from the operating cost.

The project grew into a broad product with a substantial data pipeline, account features, resume tools, and an extension. Running that scope became too costly. I stepped back from the live service and used the experience to make tighter choices about scope, data freshness, background work, and infrastructure.

THE TAKEAWAY

A feature can work and still be too expensive to keep. Operating cost is part of the design, especially when fresh data is the product.

Presented as a past engineering project. No live-service availability, current job counts, or business results are claimed. Source is private.
